# Phase 21: shared portfolio workflows

`sharedUi` presents overview, activity, accounts, reports and settings using the shared `PortfolioApplication` and platform actions. The application begins empty; example data is created only when explicitly requested. Owners, account groups, accounts, portfolios and Bitcoin mainnet public addresses are stored locally. Manual activities, classification rules, corrections, reviewed reconciliation decisions and manual prices use the existing ledger, overlay and market repositories. Activities retain source records and distinguish pending from confirmed movements. Portfolio selection scopes balances, history and activity inclusion.

The UI displays missing or stale prices, partial or unknown source coverage and source refresh status. Bitcoin history comes from a consented Esplora endpoint; the scan checks address transaction counts, mempool stability and the original chain anchor before atomically applying the observed ledger. Archived accounts leave active scopes and pause their addresses; their history and treatments remain restorable. Refresh preserves history for accounts outside its complete active scope. Reassignment of an existing tracked target is blocked after Bitcoin activity exists. These safeguards do not establish independently verified chain completeness, so source coverage remains partial after refresh.

Compact layouts below 700 dp use bottom navigation and safe insets. Wider layouts use a sidebar, with a wider sidebar from 1120 dp; content scrolls vertically. Sidebar navigation also scrolls in short landscape windows, and each page retains its own scroll position. `PolionApp.kt`, `Workflows.kt` and `AccountingPanel.kt` contain the shared screens and forms, while `PortfolioApplication.kt` owns projections and persisted workflows.

Public wallet imports support the descriptor and xpub grammar documented in [Bitcoin wallets](bitcoin-wallets.md). Discovery uses explicit bounded gap scanning, persists derived child targets atomically, and supports rediscovery. Derived addresses are presented in a scrollable detail list. Responsive UI tests cover phone, medium, wide and short landscape layouts, including enlarged text. The same deterministic Bitcoin financial workflow executes against desktop JDBC and native Android SQLite. Android lifecycle checks use an API 29 emulator, and the validated app is installed in the Pixel’s current Main profile. Provider completeness remains explicitly unverified; a full screen-reader audit is outside the executed checks. See [Milestone D](milestone-d.md) and [validation evidence](validation.md).

Archived groups retain independent descendant archive intents; restoring a group only resumes descendants with no remaining archive intent. Scoped activity rows total movements inside the selected portfolio/account intersection and retain complete source movements in details. Zero-net and mixed-direction rows use a neutral direction indicator.

Before applying a completed address scan, refresh reconstructs its transaction graph and compares active-address UTXOs with the selected provider. Valid differences are advisory: Data Health displays the persisted mismatch/missing-parent count and coverage remains partial. A matching refresh clears the warning. Invalid transaction graphs fail refresh. Graph comparison is derived from staged history and does not independently prove chain completeness.
