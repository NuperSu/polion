# Phase 23: charts, reporting and customization

The overview and reports screens use historical holdings and market observations from the same shared projection engines as textual balances. The value chart samples historical projections; the historical breakdown offers dated asset allocation, account valuations and category incoming/outgoing quantities. All use the same scoped effective ledger and saved market observations. Unpriced positions and partial coverage are identified instead of inventing prices. Display charts use approximate coordinates, while ledger quantities, prices, valuations and accounting remain exact decimal or rational values.

Activity supports search, filters and pagination. The accounting panel pages activities, lots and disposals and allows explicit acquisition, disposal and same-owner internal-transfer treatments. Missing cost and proceeds remain unknown. FIFO lots and disposal rows include exact basis, gain and consumed-lot identifiers. Bitcoin replay uses verified block height and transaction position independently of block timestamps. Unverified or mixed-source chronology leaves affected basis/gain unknown. No tax conclusion is implied.

Currency selection, manual price observations and CSV export are available. `PortfolioApplication` caches its effective ledger and holdings projection until a mutation or explicit reload; history series reuse that replay. The host serializes application calls, and a reload invalidates projections after a separate background instance writes. Filtering activity does not rebuild the historical chart or discard cached ledger replay. UI pagination bounds composed activity and accounting rows, but a full accounting report still calculates over its applicable ledger.

Historical analytics expose price status and observation IDs; accounting rows expose consumed lots and exact fractions. A 10,000-activity UI workload verifies bounded history pagination and exact search. Responsive navigation, enlarged-text and multi-leg correction tests pass. Block-position enrichment is explicit and does not block initial balance synchronization; resync preserves verified order only when block anchors and economic data still match. Reorgs invalidate that order until verification succeeds. See [Milestone D](milestone-d.md) and [validation evidence](validation.md).

Reports provides **Verify Bitcoin transaction order** for uncertain Bitcoin chronology. Android performs verification in the foreground sync service; desktop uses the serial worker. Verification reuses saved transaction provenance and fetches block transaction lists. Mixed-source ambiguity remains explicit, with affected basis/gain values unknown.
