# Bitcoin chain evidence

Each accepted address-history scan appends a scoped graph snapshot. SQLite stores its provider identity, chain checkpoint, observation time, address/account membership, raw payload checksums, transactions, input spend edges, outputs, exact values, scripts, block anchors, owned-output states, conflicts and replacement evidence. Transaction revisions are shared across snapshots; scoped validity ranges retain changes without copying unchanged graph rows. Provider UTXO differences and missing owned parents are retained with that snapshot. They remain advisory: provider history and UTXO responses are not independent chain verification.

Data health opens a paginated UTXO comparison for exactly the currently enabled Bitcoin address/account scope. Each page reads at most 100 discrepancy rows directly from normalized SQLite evidence (the UI requests 10), with reconstructed and provider amounts in exact satoshis, confirmation anchors, account/address ownership, missing-parent evidence, provider identity and observation/checkpoint metadata. A changed active scope without an accepted snapshot reports unknown evidence; older or disabled scopes are not merged into the current comparison. Paging restarts when a newer accepted snapshot replaces the displayed one. Missing graph evidence after restoring an older backup remains explicit until refresh. This review is advisory and does not overwrite balances or establish complete history coverage.

Graph state controls the materialized activity ledger. Valid confirmed transactions are confirmed; non-conflicting unconfirmed transactions are pending. Competing pending branches and their descendants are superseded until resolved. A confirmed conflicting spender reverses the losing branch and its descendants. Disappearance from a completed applicable scan reverses the earlier activity while preserving its revisions. Disabled or unscanned accounts are excluded from disappearance reconciliation. A scope snapshot does not replace another scope's coverage.

The graph, activity revisions, mismatch diagnostic, successful-refresh timestamp and scratch-state cleanup commit in one SQLite transaction. A failure preserves the previously accepted graph and ledger. Raw observations collected before acceptance remain available as provenance. Reconstruction uses SQLite scratch tables and reads one staged transaction at a time. Provider comparison retains one address response at a time. Scope membership and diagnostic snapshot export can still be materialized in memory; a large constrained-memory end-to-end test remains outstanding.

Before scanning a successor, Polion verifies the highest saved checkpoint against the selected provider. A canonical checkpoint permits normal refresh even after a long offline interval. A mismatching checkpoint invokes the reorg detector, which requires an actually fetched matching ancestor within 100 blocks of the current tip. Accepted shallow reorganizations discard pending scratch state and replay complete watched history. A lagging provider, unavailable ancestor, or reorganization beyond this bound leaves accepted state unchanged. The application reports that full-history recovery is required when automatic continuity cannot be established. Sources & sync offers an explicit full history recovery action. It requires provider consent and confirmation of a complete active-address rescan, discloses additional provider traffic, and preserves accepted records until replacement validation succeeds. Android runs this user-started work in its foreground sync service; desktop uses its sync worker. Scheduled and ordinary refreshes retain bounded continuity checks.

Possible replacement evidence records competing pending spends, including a disappearing pending transaction and a newly observed spender of the same input. A confirmed conflicting spender supplies confirmed replacement evidence. Neither a pending competition nor a disappearance alone proves which transaction the network accepted.

Graph tables use additive database schema version 6 and participate in encrypted portable backups. Version-5 snapshots remain readable; version-4 archives restore with empty graph evidence until a successful refresh. Existing ledger and raw provenance remain available after that restore.

Deterministic tests cover graph reopen, exact metadata, conflict descendants, replacement evidence, scope preservation, atomic rollback, older archive restore, shallow reorg acceptance, deep/no-ancestor rejection, lagging providers and long offline intervals. These tests do not close independent real-chain financial acceptance, descriptor-library audit, or the remaining product/device acceptance gates.
