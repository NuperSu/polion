# Phase 22: platform integration and privacy

Android and desktop open local SQLite stores and use a shared serial dispatcher for application work. User-started Android sync runs in `BitcoinRefreshService`, independently of the activity, with a data-sync foreground notification and a bounded wake lock. Android's `RefreshWorker` schedules network-constrained periodic work through WorkManager; desktop uses a scheduled refresh while running. Android database initialization runs off the UI thread. Shared status flows display progress without waiting on the database queue. Requests require explicit source consent. Source addresses and network metadata are visible to the selected public indexer; the settings workflow explains this boundary. The HTTPS transports restrict paths, do not follow redirects and limit response sizes.

Esplora requests run on the network worker with at least one second between attempts. Explicit HTTP 429 responses allow two retries per request, with exponential waits starting at two seconds; each refresh transport allows at most six retries and 30 seconds of retry waits. `Retry-After` delta seconds and HTTP dates extend those waits. A cooldown exceeding the wait bounds ends that refresh without sending an early retry. Exhausted transports reject further requests; a new refresh creates a fresh budget. Fixed progress messages show the cooldown and retry count. Cancellation, consent and the selected endpoint are checked before attempts and every 100 ms during waits; active network operations retain their 10-second connect and 20-second read timeouts. Desktop shutdown interrupts the sync worker and closes its database only after the worker finishes, with termination waiting on the host worker queue. Other provider errors and malformed responses propagate without transport retries. Conservative pacing can make large scans exceed Android's background time allowance; interrupted scans retain their staged history and resume through the normal refresh workflow.

Both hosts offer file selection for CSV export and password-encrypted portable backups. Restore decrypts and validates into a separately initialized staging database before the host replaces the live file. The Android privacy-lock verifier is protected with a Keystore AES-GCM key; the Linux desktop verifier is stored in Secret Service through `secret-tool`. Existing verifier files migrate after successful authentication. This lock is a screen barrier: **the live SQLite database is plaintext**, and the verifier does not encrypt it. Portable backups use authenticated encryption. A disposable desktop runtime check exercises actual Secret Service store, lookup, password verification and clearing without storing a verifier in the marker file. No provider credentials are stored. New lock setup requires working platform secure storage; failures retain the local database and display a fixed diagnostic. Local data erasure enables SQLite secure deletion, deletes application rows while retaining platform locale metadata, rebuilds free pages and truncates the WAL. Cleanup failures require retrying erasure. This purges active database files; external backups and storage-device forensic remnants are outside this operation. Android document reads and writes run on a lifecycle-owned worker with main-thread result callbacks and cancellation on activity destruction.

`androidApp` contains the activity, foreground service, worker, notification and document-picker integration; `desktopApp` contains the desktop host and file dialogs. `core/backup` implements the portable archive and encryption, and `core/application/PortfolioApplication.kt` coordinates export and restore. Logging must not include addresses, source payloads, secrets or free-form exception text.

An API 29 emulator has executed the real SQLite and crypto bindings: persisted projection/reopen, authenticated backup restore with a wrong password, full-database rollback and password verification. A UI check force-stops and restarts the app, rejects a wrong lock password, then unlocks with the correct one. A real public-address fixture sync remains a foreground service after switching to Home and completes on return. Airplane-mode sync preserves the complete fixture ledger and reports a clear provider error. WorkManager retries while a manual sync is active, completes the scheduled fixture refresh, and registers the next 30-minute job. A force-stop during an active scan leaves an interruption notice and preserves the ledger and endpoint; retry completes successfully.
